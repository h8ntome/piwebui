# Good first issues

Five scoped tasks with the files each one touches. They are real gaps found while auditing the
repository, not make-work. Each is small enough to review in one sitting, and none requires changing
runtime behaviour.

> Create these with `gh issue create --repo <owner>/pi-web --label "good first issue" --title ... --body-file ...`
> once the repository exists. Do not paste all five on the same day; one open question is a nicer
> repository than five.

## 1. Show the pi version and validation state in the UI footer

**Why:** the whole app fails closed when the installed pi is not the validated 1.5.0, but the browser
gives no hint that this happened. A user sees features silently disabled.
**Where:** `packages/client/src/App.tsx` (footer/header area), the health payload in
`packages/server/src/routes.ts` (already reports `resolvedVersion` and `tested`).
**Do:** render `pi <version>` plus a small "unvalidated" marker when `tested` is false.
**Acceptance:** with a matching pi the footer shows the version; when the version gate fails the marker
is visible without opening devtools. No new endpoint. Add or extend one unit/e2e assertion for the string.

## 2. Give `--data-dir` a `PIWEB_DATA_DIR` environment fallback

**Why:** every documented command repeats `--data-dir`, which is friction in shell snippets and systemd
units, and it is easy to start a server against the wrong store.
**Where:** flag parsing in `packages/server/src/main.ts` (`parseFlags`), the CLI banner text.
**Do:** read the env var when the flag is absent; print which directory is in use at startup (already
done, keep it). Precedence: explicit flag > env var > default.
**Acceptance:** `PIWEB_DATA_DIR=/tmp/x pi-web serve --port ...` uses `/tmp/x`; the explicit flag still
wins; README CLI section and `--help` updated; one smoke assertion added if cheap.

## 3. Replace the `console` fall-through in client error paths with a typed toast

**Why:** a few client paths log to the console instead of surfacing a failure, which contradicts the
project's "a failure a user can feel must be visible" rule.
**Where:** grep `console.` in `packages/client/src/` (start with `api.ts`, `store.ts`, `sse.ts`).
**Do:** route each through the existing error/notification state; delete a console call only when a
visible message replaces it.
**Acceptance:** no bare `console.log`/`console.error` remains for user-facing failures; the change is
limited to error presentation and touches no protocol code.

## 4. Add a `npm run check` aggregate script and use it in CI

**Why:** three commands are run in the same order in CI, in CONTRIBUTING and by hand; the aggregate is
one line to remember and one line to change.
**Where:** root `package.json` scripts, `.github/workflows/ci.yml`, `CONTRIBUTING.md` testing table.
**Do:** `"check": "npm run typecheck && npm run test:unit && npm run build"`; CI calls `npm run check`.
**Acceptance:** CI green with the aggregate, docs updated to match, no duplicated command list left
anywhere.

## 5. Make `docs/CAPABILITY_MATRIX.md` fail the build when it drifts from the code

**Why:** the matrix is the README's receipts. It is generated by `e2e/p0-capability-matrix.ts` today,
but nothing checks that the committed file matches a fresh run, so it can go stale silently.
**Where:** `e2e/p0-capability-matrix.ts` (it already writes the file), plus a CI step.
**Do:** add a `--check` mode that regenerates in memory and exits non-zero on difference; call it in CI
after the matrix can run, or as a `workflow_dispatch` job if it needs a live pi.
**Acceptance:** editing one row of the committed markdown makes the check fail with a diff; a fresh run
with no drift passes. Document the mode in `docs/CHECKS.md`.
